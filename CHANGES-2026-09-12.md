# CampusConnect — update notes & manual steps (2026-09-12)

These notes cover the changes made in this round and the few **manual steps** you
must run locally, because the build/compile tools could not be run in this
environment (the isolated Linux sandbox lost access to the project files, so all
changes were made and verified by source inspection only).

---

## What changed this round

### 1. Volunteer coordinator controls now actually work ("add operations")

The event **Volunteers** tab (`frontend/src/pages/manage/eventTabs.tsx`) was a
read-only list. It is now a full coordinator panel:

- **Assign volunteer** — pick an *active* volunteer from the event's club, set a
  role, location, shift start/end and check-in duty, and assign them.
- **Add task** — give an assigned volunteer a titled task with description,
  instructions, location, priority and a start/end window.
- **Cancel assignment** — remove a volunteer from the event (with confirmation).
- A **Tasks** section lists every task with priority and status badges.

**Root cause of "operations not working":** the volunteer shift/task datetime
fields are typed as `Instant` on the backend, but an `<input type="datetime-local">`
produces a *zone-less* string (e.g. `2026-09-20T09:00`) that the server cannot
parse into an `Instant`. The panel now converts every datetime to a proper UTC
ISO string (`new Date(local).toISOString()`) before sending, so the POST
succeeds. The backend was intentionally **not** changed (no rebuild).

### 2. Club-member dashboard

Club members previously landed on the plain student dashboard, which showed
nothing about their membership. `frontend/src/pages/app/DashboardPage.tsx` now
shows a **"Your club membership"** section (only for the `CLUB_MEMBER` role) with
a card per club they belong to and quick access to the **check-in scanner** — the
member-only tool that was otherwise buried in the sidebar. No new route or page
was added, so nothing is duplicated.

> The coordinator, student and volunteer dashboards were already redesigned with
> stats, charts and action buttons in the earlier rounds; they were left as-is to
> avoid duplicating existing work.

## Required manual steps

Run these on your machine, in order.

### 1. Delete the stray Vite config artifacts

`frontend/vite.config.ts` is the real config. Two stale compiled copies exist and
should be removed so tooling doesn't pick up the wrong one:

```bash
cd campusconnect/frontend
rm vite.config.js vite.config.d.ts     # keep vite.config.ts
```

(On Windows PowerShell: `Remove-Item vite.config.js, vite.config.d.ts`)

### 2. Build the frontend

```bash
cd campusconnect/frontend
npm install
npm run build          # runs: tsc -b && vite build
```

`tsc -b` is the type-check gate (strict mode with `noUnusedLocals` /
`noUnusedParameters`). All edits this round were kept import-clean by inspection,
but this is the authoritative check.

### 3. Build the backend

```bash
cd campusconnect/backend
mvn compile            # Maven must be installed; there is no ./mvnw wrapper
```

No database migration is needed: the app runs with `spring.jpa.hibernate.ddl-auto=update`,
so the volunteer assignment/task tables and columns are created/updated automatically.

### 4. (Optional) Turn on the in-app AI assistant

The help chatbot is **off by default** and the widget stays hidden until it is
configured — so you don't have to do anything if you don't want it. To enable it,
set these environment variables for the backend before starting it:

```bash
AI_ENABLED=true
AI_API_KEY=sk-...                       # your provider key — server-side only
AI_PROVIDER=openai                      # label only
AI_BASE_URL=https://api.openai.com/v1   # any OpenAI-compatible endpoint
AI_MODEL=gpt-4o-mini
```

Security notes (already enforced in code):

- The API key lives only on the server; it is **never** sent to the browser.
- `/api/assistant/**` requires authentication (falls under the default
  `anyRequest().authenticated()` rule).
- The system/grounding prompt is set server-side; the client can only send
  `user`/`assistant` turns, and requests are rate-limited per user.
- When `AI_ENABLED=false` or no key is set, `GET /api/assistant/status` returns
  `enabled:false` and the widget renders nothing.

Because `tsc`, `npm` and `mvn` could not be executed here, correctness was checked
by reading the source:

- Every symbol used in the new UI is imported and used (no unused imports/locals),
  including the icons `Ban`, `ClipboardList`, `UserPlus`, `QrCode`, `Avatar` and
  `formatDate`. The unused `VolunteerTaskResponse` import was removed.
- All service methods exist with matching signatures: `volunteerService.forEvent`,
  `tasksForEvent`, `forClub`, `assignToEvent`, `createTask`, `cancelAssignment`,
  and `eventService.getById` (returns `EventResponse.clubId`).
- All referenced DTO fields exist on `VolunteerResponse`,
  `VolunteerAssignmentResponse`, `VolunteerTaskResponse` and `ClubMemberResponse`.
- Component props match: `Field` (`required`/`htmlFor`), `EmptyState` (`action`),
  `ConfirmDialog` (promise-aware `onConfirm`), `Modal`, `Select` (children).
- The backend assistant files are all present, `app.ai.*` is in `application.yml`,
  and `/api/assistant/**` is not in the `permitAll` list.

**Still recommended:** run steps 2 and 3 above — they are the real compile gates.
