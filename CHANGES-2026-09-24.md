## 1. Why payment was still instant ("coming like that only")

Real Razorpay payments were already coded. They only turn on when the **running**
backend sees `PAYMENT_PROVIDER=razorpay` + the keys. Three things blocked that:

1. **Wrong file.** Your keys were in `.env.example`. Nothing reads that file — it is
   a *template* you copy to `.env`. (It's also committed to git, so putting real
   secrets there leaks them — see §4.)
2. **Split across two templates.** The root `.env.example` had the Razorpay/Twilio
   keys, but `backend/.env.example` (the one a local run would use) still said
   `PAYMENT_PROVIDER=mock` with **blank** Razorpay keys. So even if you had copied
   it, it would still be mock.
3. **Spring Boot doesn't read `.env`.** For a local `cd backend && mvn spring-boot:run`,
   Spring only reads OS environment variables / `application.yml` — not a `.env`
   file. The README even said "…then **export them**", which is easy to miss.

### The fix
- Added a tiny, standard dependency **`me.paulschwarz:spring-dotenv`** to
  `backend/pom.xml`. It auto-loads `backend/.env` into Spring's config when you run
  from `backend/`. (It's a no-op under Docker, where Compose injects the variables.)
- Created **`backend/.env`** (git-ignored) with your real values and
  `PAYMENT_PROVIDER=razorpay`. This is the file that actually turns real payments on.
- Created **root `.env`** (git-ignored) for the Docker path too.

You do **not** need to export anything by hand anymore.

## 5. The Vite `ws proxy socket error: read ECONNRESET`

That error is **not a bug in the app** — it means the dev server tried to reach the
backend WebSocket (`/ws` → `127.0.0.1:8080`) and **the backend wasn't up** (not
started yet, still booting, or it failed to connect to the DB and exited). The proxy
config was already correct.

I softened it so instead of a scary repeating stack trace you now get one line:

```
[dev proxy] backend not reachable at http://127.0.0.1:8080 (ECONNRESET).
Start the backend first (cd backend && mvn spring-boot:run), then reload the page.
```

The real fix is **start order**: bring the backend up first, confirm
`http://localhost:8080/swagger-ui.html` opens, then start/reload the frontend.
If it persists, your backend is failing to start — check its console for a MySQL
connection error to your Railway DB (see §7 step 1).

## 7. Step-by-step: run it and take a real payment

### Step 1 — Start the backend (reads `backend/.env` automatically now)
```bash
cd backend
mvn spring-boot:run
```
Wait for `Started ...Application`. Then open **http://localhost:8080/swagger-ui.html**
to confirm it's up. In the startup log you should see the active provider, e.g.
`payment provider: 'razorpay'` and `WhatsApp providers registered … active: 'log'`.
If it exits with a MySQL error, your Railway DB is unreachable — check the URL /
password in `backend/.env` and that the Railway instance is running.

> First run only: `mvn` will download `spring-dotenv`. If you're offline, run once
> with internet so Maven can fetch it.

### Step 2 — Start the frontend
```bash
cd frontend
npm install          # first time only
npm run dev          # http://localhost:5173
```

### Step 3 — Pay for real
Log in, open a **paid** event, click **Pay/Register**. Instead of an instant ticket
you'll now get the **Razorpay checkout**. Use a Razorpay **test card**, e.g.
`4111 1111 1111 1111`, any future expiry, any CVV, and complete it. The ticket +
QR is issued **only after** Razorpay confirms and the server verifies the signature.

### Step 4 — Confirm delivery
After a successful test payment: the **email** ticket sends via Brevo (check the
inbox / your Brevo activity log). The **WhatsApp** message is currently logged to the
backend console (provider `log`). To send it for real, fix the three Twilio TODOs in
`backend/.env` (§2) and set `WHATSAPP_PROVIDER=twilio`.

### (Optional) Docker instead of local
```bash
docker compose up --build     # reads the root .env; app on http://localhost:8081
```
